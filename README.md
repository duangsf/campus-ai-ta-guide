### 核心指标（可现场复现）

```
检索策略消融评测（56 题人工标注，含 8 题应拒答）
────────────────────────────────────────────────────────────────
检索策略                     R@1     R@3     MRR    兜底准确  误答率  可答率   耗时
① v1 关键词子串匹配（无闸门）  81.3%   81.3%   0.813   25%     75%    91.7%   0.46ms
② v1 检索 + 置信度闸门        81.3%   81.3%   0.813  100%      0%    89.6%   1.01ms
③ v2 三路融合检索（不开闸门）  79.2%   91.7%   0.859   12.5%   87.5% 100%     0.45ms
④ v2 完整方案（融合 + 闸门）   79.2%   91.7%   0.859  100%      0%    97.9%   1.06ms
```

- **Recall@3：81.3% → 91.7%（+10.4 个百分点）**
- **MRR：0.813 → 0.859**，正确条目排得更靠前
- **兜底准确率：25% → 100%**，**误答率：75% → 0%**（幻觉抑制的直接证据）
- 分组细项：直接命中 20/20 · 同义改写 16/20 · 多跳推理 8/8 · 兜底保护 8/8
- 单次检索耗时 **1.06ms**（纯本机计算，不消耗任何 API 额度）

> 评测方法学：四组对照是**同一份代码的开关对比**（消融实验），不是三套代码横向比较；
> 阈值由 `tools/calibrate.js` 网格搜索标定，选阈值准则是"兜底准确率 ≥95% 前提下最大化召回"——
> 因为校园问答里一次编造事实的代价远高于一次礼貌拒答。

### 为什么检索引擎要"同构"

`src/rag.js` 用 UMD 包装，**Node 与浏览器加载的是同一份代码与同一份数据**。
这样带来两个好处，也是答辩时能经受追问的关键：

1. **界面展示的检索过程 = 服务端真实的检索过程**，不存在"演示一套、背后一套"；
2. 离线模式与云端模式**共用同一个闸门判据**，切换模式不会出现两套表现。

## 四、RAG 链路：九个可被评委逐帧验证的步骤

提问后右侧抽屉会实时展开整条链路（点右上角「🔍 RAG 链路」）：

| 步骤 | 展示内容 | 对应实现 |
|---|---|---|
| ① 查询理解 | 意图分类、实体链接、N 条查询改写 | `intentOf` / `linkEntities` / `rewriteQueries` |
| ② 分词与关键词抽取 | 实际参与检索的词项（词典词高亮、未覆盖词标红） | `tokenizeDetailed` |
| ③ 三路召回 | 候选数、语义向量维度、图谱命中实体与多跳路径 | `bm25` / `vectorScore` / `graphScore` |
| ④ 融合重排 | 0.45×BM25 + 0.35×向量 + 0.20×图谱，Top5 分数条与三路分解 | `retrieveDetailed` |
| ⑤ 置信度闸门 | 置信度 vs 阈值仪表盘 + 文档覆盖/词表覆盖 + 未覆盖词 | `gateDecision` |
| ⑥ Prompt 注入 | 实际送进模型的知识片段（与来源标注同一份数据） | `toolSearch.payload` |
| ⑦ 流式生成 | **答案首字延迟**（用户感知）与首次响应延迟分开统计 | SSE `first_answer` |
| ⑧ 引用核验与落库 | 端到端耗时、工具轮数、来源数、sqlite 记录号 | `db.logQA` |

### 置信度闸门：为什么"不回答"比"答错"更重要

闸门由三个判据相乘而成，任何一个掉下来都足以让系统选择不回答：

```
置信度 = 检索强度 × min(文档级覆盖, 词表级覆盖)     （均做长度归一化）
         ↓                    ↓
    0.55+0.45×Top1分    查询实词落在候选条目/全库中的比例
```

设计过程中在这里踩过几个必须记录的坑（均已写入回归测试）：

- **只靠分数无法判断"未收录"**：各路线分数都做过 max 归一化，Top1 恒为满分，
  于是"食堂三楼川菜窗口的招牌菜"和"图书馆几点开门"会拿到同样的最高分。
  真正有区分度的问题是：**问题里的具体词，知识库里到底有没有** → 引入覆盖率判据。
- **覆盖率会被分词碎片污染**：早期分词产出 `馆几 / 怎么申 / 么申 / 么申请` 这类跨词 n-gram，
  它们天然不在任何文档里，把正常提问的覆盖率系统性压低。修法是**召回分词与闸门分词分离**：
  召回侧保留 2-gram 兜底（容忍未登录词），闸门侧只用词典整词（判定主题覆盖）。
- **稀有碎片会主导 BM25 排序**：`么申` 只出现在 2 个文档里（IDF 3.98），而真实主题词
  `申请` df=26（IDF 1.62）—— BM25 天然偏爱稀有词，结果正确条目被挤出 Top1，
  表现为"加了三路召回，R@1 反而比 v1 还低"。修法是给查询侧兜底 n-gram 加**信息量降权**。
- **阈值必须用数据定，不能拍脑袋**：`tools/calibrate.js` 网格搜索，
  判据是"兜底准确率 ≥95% 前提下最大化召回"。

### 域外意图识别（Out-of-Scope）

有些问题用词在语料里出现过，覆盖率不为 0，但**在意图上**就不属于校园问答范围。
这类靠分数兜不住，必须显式识别（命中即明确拒答并说明理由）：

编程算法 · 实时天气 · 实时行情/每日菜单 · 个人隐私 · 账号凭据 · 医疗诊断 ·
法律与心理诊断 · 其他院校对比 · 通用翻译写作 · 数学解题

现场演示建议用这两条探针（快捷提问区末尾已内置）：
- 「今天食堂的午饭菜单有什么菜？」→ 实时数据无法预先收录，演示**诚实拒答 + 自动建工单**
- 「帮我写一段 Python 快排代码」→ 演示**服务范围边界**

## 五、Agent 工具集（7 个）

服务端 Agent 循环负责"决策 → 调工具 → 再决策 → 生成答案"，全程以 SSE 事件推给前端：

| 工具 | 作用 | 演示场景 |
|---|---|---|
| `search_campus_knowledge` | 三路融合检索 + 闸门 | 基础校园问答，带来源标注 |
| `traverse_knowledge_graph` | 图谱多跳关系扩散 | "从宿舍出发最近的自习室" |
| `query_live_status` | 按**当前时间**算场所开放状态 | "现在还能去哪里自习" |
| `navigate_to` | 生成步行路线，联动地图飞行 + 路径流光 | "从宿舍到图书馆怎么走" |
| `plan_form_fill` | 办事材料清单 + 办理步骤 | "补办学生证要什么材料" |
| `create_ticket` | 未收录问题自动建"知识盲区"工单 | 拒答后闭环 |
| `handoff_to_human` | 转人工并返回部门联系方式 | 隐私/学籍/投诉类问题 |

**工具返回体的设计**：统一结构 `{ summary, payload, sources, trace, detail }`，
其中 `payload` 给模型看、`trace/detail` 给界面看（驱动地图联动）。
两者同源，避免"界面显示的与实际注入的不是一回事"。

## 六、已修复的重要缺陷（含"模型请求一直重试"）

### 1. 模型请求反复重试 / 空转（重点）

**现象**：聊天时上方模型请求会不断重复发起，迟迟不给答案。

**根因**（三个问题叠加，已逐条修复并加回归断言）：

| 问题 | 说明 | 修复 |
|---|---|---|
| 工具结果回灌体积失控 | `payload` 里带着 `trace`/`detail`/`sources`（含完整条目正文），一次检索可能把几十 KB 结构噪声塞进对话上下文，模型被干扰后会反复调用同一工具 | 服务端 `forModel()` 只回灌 `payload` 并设 **3000 字符硬上限** |
| 无重试保护与退避 | 网络抖动/429/5xx 时没有重试；若中途重试还可能造成前端文本重影 | `llm.js` 有界重试（≤3 次，指数退避+抖动），并设**安全重试点**：一旦已推送 delta 绝不重试 |
| 缺少防重复调用约束 | 模型拿到资料后仍可能继续要求检索 | 回灌已调用工具名 + 最后一轮不下发工具 + 追加"立即作答"硬约束；若仍无内容则明确报错而非静默返回空 |

**验证**：`node _测试\test-api.js --live` 中三条用例分别断言
"零 error 事件 / 工具调用次数 ≤3 / `final.rounds ≤ 3`"。

### 2. 其他静默出错的坑（均已成为回归测试）

| # | 缺陷 | 后果 | 现已断言 |
|---|---|---|---|
| ① | `loadData` 把 `{meta,entries}` 包装对象当数组 | **语料 61 条静默丢失**，索引只有 60 条 | 回归① |
| ② | `retrieveDetailed` 的 top 结果漏带 `entry` 字段 | 闸门收到空对象 → **文档级覆盖恒为 0**，几乎所有问题被判"未收录"（这个 bug 会静默毁掉全部评测数字） | 回归②③ |
| ③ | `coverAgainst` 空查询提前返回缺字段 | `/api/rag` 空查询 500 | 回归④ |
| ④ | 分词产出跨词 3-gram 碎片并进入查询 | 稀有碎片高 IDF 把正解挤出 Top1，R@1 反而低于 v1 | 回归⑨ |
| ⑤ | 数据库 schema 变更 | 升级代码必须删库，历史演示数据丢失 | 新增 `migrate()` 自动补列 |
| ⑥ | 延迟指标口径混淆 | 把"模型决定调工具"的时间当成用户等待时长，指标失真 | 拆分为「答案首字延迟」与「首次响应延迟」 |

### 3. v1 遗留的安全问题

v1 的 `index.html` 里**明文硬编码了 API Key**（且每次初始化覆盖 `config.js`，导致"本地知识库模式"测试必然失败）。
v2 **已彻底移除**：Key 只从页面设置（存本机 localStorage）或环境变量读取，不写入任何代码文件。

> ⚠️ 请务必到火山方舟后台**吊销 v1 里那个 Key 并重建**，它已经出现在代码与对话记录中。

### 4. 3D 沙盘：从"方块 + 空底板"到"按校园边界生成的沙盘"

初版 3D 场景有两类肉眼可见的问题，都已修复并被 `tools/check-camera.js` 数值化断言：

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| ① | 底板固定为 **1050×1050** 大方块，而校园实际只占 876×854 | 四周留一大圈**空沙盘**，既占画面又显得空 | 底板改为按 `places.json` 外接矩形 + 45 m 边距生成 → **966×944 m（96.6×94.4 世界单位）**，紧贴校园，空地消除 |
| ② | 取景按"建筑内容"而非"底板"算距离 | 底板被裁掉 **94%** | `_fitDistance()` 改为按底板四角迭代求解 |
| ③ | 用"四角包围盒居中"当相机目标 | 正交投影下包络不对称（左侧两角 NDC 都是 −0.577），底板中心被推到画面 62% 高度 | 加**两遍法**：先按底板几何中心取景，再按投影包络偏移量平移校正 |
| ④ | 透视相机试图给地面板居中 | 倾斜俯视地面**几何上不可能**同时让底板与建筑群都居中 | 默认视角改为**正交（沙盘/轴测）**，几何上严格居中；透视保留作"漫游"（其建筑群中心在 41.6%，属透视固有特性） |
| ⑤ | 楼宇是简单方块、彼此重叠 | 观感差、比例失真 | 程序化立面贴图 + 坡屋顶 `BufferGeometry`；布局改由 `tools/gen-layout.js` 声明式生成，`tools/check-layout.js` 独立校验**无重叠/间距合规/尺寸合理** |

**当前实测**（画布 787×458）：建筑群中心 **(50.0%, 50.0%)** 精确居中，铺开水平 23%~83%、垂直 17%~83%，
四角最大 |NDC| 0.990 —— 饱满且不裁切。

### 5. 改了代码刷新却没变化（静态缓存）

静态资源原先统一 `Cache-Control: public, max-age=300`，**改完 js/css 刷新页面浏览器仍用旧文件**，
表现为"我明明修了但页面没变"（本项目 3D 取景的反复返工有一部分就是这个原因）。
现改为：源码类（`.html/.js/.css/.json`）一律 `no-cache, no-store, must-revalidate`，
只有图片/字体才允许缓存。`vendor/three.module.min.js` 也走禁缓存 —— 演示前改完刷新即生效，
比省一次 670 KB 下载更重要。

## 七、数字人口型同步：一个必须说清楚的技术边界

浏览器的 Web Speech API（`speechSynthesis`）**不提供音频输出流**，
因此**无法**用 Web Audio 分析 TTS 的真实波形。网上不少"数字人口型同步"演示
实际是随机抖动或固定循环，并没有与语音对齐。

本项目的做法是「**文本驱动的音素-口型映射 + 语速包络**」：

1. 把播报文本切段，估算每字时长（中文约 5.2 字/秒，标点加停顿）；
2. 逐字查韵母-口型表（开口度 / 圆唇度 / 横向展开度）得到 viseme 序列；
3. 两条正弦叠加模拟自然语流开合，避免机械抖动；
4. **预留真实音频通道**：`avatar.attachAudioStream(mediaStream)` 一旦接入云端 TTS 的
   音频流，口型与频谱会自动切换为真实频谱驱动。

答辩时应当如实说明这一点 —— **不谎称做了音频级对齐，而是提供了可替换的驱动层**。
